# Pushback: one model reviews another's answer; pictures by a chosen model

2026-10-18. Status: accepted (Kevin's decisions below; the primitive is
rho's `Rho.Consult`, built alongside).

## Context

Kevin: "We need a way for one model to direct another … In Bezalel we need
one model to be able to submit image generation via another one, or
perhaps do an internal critique akin to code review. So we should be able
to say Claude generate the answer and Gemini provide pushback." Gemini
joins as a provider by API key (rho already takes `:google` credentials).

The host-neutral parts (calling another model, its events, its cost, an
injected turn attributed to another model, the `ask_model` tool) are
rho's, shared with Operator. What a Bible-study critique checks, which
reply it reviews, and how the chat shows it are Bezalel's, the same in
both apps: so they are here.

## Kevin's decisions

- Pushback runs **both ways**: a per-conversation switch for automatic
  pushback on every reply, and on demand (a Pushback button on a reply, or
  asking in words: "have Gemini push back").
- **Critique, then the reply to it.** The first answer stays; the critique
  shows as its own block ("Pushback · Gemini 3 Pro"); the answering model
  then replies to it, revising or standing its ground with reasons.
- Pictures can be drawn by another model: OpenAI gpt-image today, Gemini
  image models added.

## Decision

- **`Bezalel.Agent.Pushback`.** The critic is the user's "Pushback from"
  (`Preferences.pushback_model`, none by default). Its brief
  (`critic_prompt/0`) is a study code review: claims against the cited
  tool results, citations that don't support their claim, textual and
  linguistic accuracy, missing or one-sided perspectives, overreach;
  numbered, most serious first, each with a severity and evidence; no
  rewrite; no confessional side (core's rule 5). It reads the question
  as the lead got it (its pictures and PDFs by reference), every tool
  call of the reply with its result (capped: 4,000 characters each,
  24,000 in all, Source lines kept) and the answer, not the whole
  conversation: that is what a review of this answer needs, and it
  bounds the cost.
- **One round per reply**, decided from the session alone
  (`target/1`): the last reply, finished with an answer; refused when it
  is the lead's answer to a critique, already has one, or had one within
  its turn (the lead's own `ask_model` critique: asking in words is a
  way in, so it uses the round too). No flag to keep in sync: the
  attributed `model_message` entry (or the `ask_model` call) is the
  record. A failed answer to a critique leaves the critique
  (`drop_after_question/1` stops at it); deleting the critique allows
  another round. `offered?/2` decides the same from the messages
  (`Message.stop_reason`, the CONSULT blocks).
- **Only the last reply** can be pushed back on: the critique is
  appended to the branch, and the lead's answer to it belongs right
  after the reply it reviews. `offered?/2` tells the apps where the
  button goes.
- **The critique is the critic's own message**, stored by rho
  (`Rho.Loop.prompt/3` with `attribution: {:model, model, "critique"}`
  and `instruction:` "Respond to each point: revise where it's right,
  stand your ground with reasons where it isn't…"), so the lead sees it
  marked as another model's, not the user's, and the transcript reads it
  back as a `:consult` `Message` (`model`, `purpose`, `text`, one CONSULT
  block). The instruction travels with the entry, not in the system
  prompt, so it is only there when a critique is.
- **Runs in a task** under rho's task supervisor (`start/3` returns at
  once). What can fail before spending anything is checked first and
  answered as a sentence for the user (no critic chosen, the critic's
  provider not signed in, a reply running, nothing to review, the round
  had). After that the loop's event stream is the only channel: the
  critique streams as `consult_*` events into a reply the app starts
  with `Reply.pushback/4`; other replies ignore consults outside a turn,
  so a critique is never drawn in the user's next reply.
- **A failed critique is not a failed run.** It ends the pushback reply
  `:done` with `reason: :consult_failed` and the error, not `:error`:
  the apps' failed-run path drops the run's entries and asks again,
  which here would delete the answer under review.
- **A critique that comes back after the user moved on is dropped**,
  not queued: answering it after the new reply would break "critique,
  then the reply to it" (Kevin's display), and the critique was shown
  live. The round isn't used, so the user can push back again.
- **Asking in words** uses rho's `ask_model` tool inside the lead's turn:
  `Prompt.other_models/0` (only when the host offers the tool, so the
  prompt never names a tool the model hasn't got) says to ask only when
  the user asks, once, then answer each point. `Pushback.system/1` is
  rho's `:consult_system` hook, so that critic gets the study brief too.
  Its result shows as a CONSULT block in place of the TOOL CALL.
- **Pictures by** (superseded in part by
  `2026-10-18-pictures-by-chatgpt-sign-in.md`: ChatGPT on the user's
  sign-in is a choice too, none chosen is the default, and the call can
  name a model) (`Preferences.image_model`, one of
  `DrawImage.models/0`): `openai:gpt-image-2` (default),
  `google:gemini-3.1-flash-image`, `google:gemini-3-pro-image`. Imagen is
  left out: llm_db marks every Imagen model deprecated, and it takes no
  reference picture. Gemini gets the shape as an aspect ratio, asks for a
  picture only, and takes a reference as a picture beside the words. A
  missing key is named for the chosen provider, with where to add it or
  to choose another model. The tool's description stays the same whatever
  the setting (rule 5).

## Consequences

- bezalel_core needs rho `~> 0.3` (consults, attributed model messages).
- The apps: Settings → Models gets Gemini (API key), "Pushback from" and
  "Pictures by" (both stored in the study preferences); the conversation
  gets the switch (the app's, per conversation) and the button; the chat
  draws a CONSULT block (title `Pushback.title/2`, collapsible) and a
  `:consult` message, and its stream rule hides stored messages whose
  entries a live reply has `seen` (the critique included); the apps set
  `config :rho, :consult_system, {Bezalel.Agent.Pushback, :system, []}`
  and pass `ask_model: true` with `Rho.Tools.Consult` registered.
- A critique costs a second model call per reply when the switch is on;
  rho records it in the session's totals.
