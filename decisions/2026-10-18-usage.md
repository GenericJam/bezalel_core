# Usage: what's left, and why a call failed, in core

2026-10-18. Status: accepted.

## Context

Kevin: "We also need to show usage so if the user is out of tokens it's not
a mystery what happened. How many tokens left, etc." rho already records
everything needed (`Rho.Usage`: each subscription's windows from the
providers' headers and usage endpoints, the last 429, tokens and cost per
model per day), but each app read it its own way (the website only showed
tokens this week per model), and a failed call reached the chat as rho's
raw text ("Model call failed (HTTP 400): Your credit balance is too low…").

## Decision

- **`Bezalel.Usage` in core** turns rho's record into plain data both apps
  draw: a summary per signed-in provider, a meter line for the model in
  use, a reply's own usage (`Bezalel.Library.Message.usage`), a preflight
  check before sending, and `explain/2` for a failed call (kind, title,
  message, one action, the reset time, the billing page). The wording is
  shared, so the phone and the web say the same thing.
- **A subscription shows windows; an API key shows spend.** The providers
  publish no balance for an API key, so a key shows what it spent today
  and this week (rho's cost from token prices) and links the provider's
  billing page; running out is recognised from the error (Anthropic's
  "credit balance is too low", OpenAI's `insufficient_quota`).
- **`explain/2` reads the error text.** The loop reports a failed call only
  as `Rho.LLM.describe/1`'s text (the turn's `error`, the session entry's
  `errorMessage`), so the classes are recognised from that text (rho's
  own phrases, and the providers' messages it carries), with the usage
  record supplying the reset time. A `Rho.LLM.error()` term is taken too,
  for a host that holds one. Out of credit is checked before a 429, since
  OpenAI's `insufficient_quota` arrives as one.
- **The preflight stops a question** to a provider whose limit is used up
  for more than a minute (the same threshold as `Rho.LLM.usable/3`), with
  the explanation, instead of sending a call that can only fail.
- **A window at 80 % warns.**

## Consequences

- A change to rho's describe wording can break a class; the tests build
  each error from a real provider body through req_llm and rho's own
  normalise/limit/describe, so such a change fails here first.
- rho still retries OpenAI's `insufficient_quota` as a throttle before
  failing (reported to rho); the explanation is right either way.
- An API key's "left" is unknowable from here; the billing page is the
  answer.
